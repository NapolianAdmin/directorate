FINDINGS (ranked, most exploitable/highest blast radius first)

**1. Unhandled `ValueError`/`OSError` from `fxconv/cache.py` crashes `cli.main()` with a raw traceback, leaking local filesystem paths — violates the module's own "no exception may propagate out of main()" contract**

- `fxconv/cache.py:96` and `fxconv/cache.py:130` — `_cache_path()` is called *outside* the `try/except` block in both `get()` and `set()`, so the `ValueError` it raises for a malformed currency code (or the `OSError` a bad-but-regex-passing filename triggers) is never caught inside `cache.py`.
- `fxconv/cli.py:92-96` — `main()` only catches `rates.RatesError`:
  ```python
  try:
      result = convert(args.from_currency, args.to_currency, args.amount)
  except rates.RatesError as exc:
      print(f"{PROG}: error: {exc}", file=sys.stderr)
      return 1
  ```
  `ValueError` (and `OSError`) are not `rates.RatesError` subclasses, so they propagate straight out of `main()` and crash the interpreter with a full traceback.
- **Attack**: any malformed `from_currency`/`to_currency` — not just a deliberate traversal payload, a plain typo like `usd` triggers it too — reaches `cache.get()` before `rates.fetch_rate()` is ever called, so `InvalidCurrencyCode` handling is *never reached* for this class of input.
- **Reproduction (real command run against the repo)**:
  ```
  $ python -m fxconv "../../etc/passwd" EUR 10
  Traceback (most recent call last):
    File "...\fxconv\cache.py", line 76, in _cache_path
      raise ValueError(f"invalid currency code: {from_currency!r}")
  ValueError: invalid currency code: '../../etc/passwd'
  EXIT CODE: 1
  ```
  Confirmed a second time with an ordinary typo (`usd` lowercase) — same crash, same traceback shape, proving this isn't contrived-payload-only.
- **Why the test suite missed it**: `tests/test_cli.py:129` mocks `cache.get` to return `None` and `rates.fetch_rate` to raise `InvalidCurrencyCode` directly — it never exercises the real `cache._cache_path()` validation path.
- **Exploitability x blast radius**: High exploitability (trivial, zero-skill, any malformed argv including typos) x Low-Medium blast radius (local single-user CLI; the traceback discloses the local username/directory to the same user running the tool — a robustness/DoS-shaped bug with a minor local info-disclosure flavor).

**2. `CURRENCY_CODE_RE = re.compile(r"^[A-Z]{3}$")` uses `$` instead of `\Z`, silently accepting a trailing newline**

- `fxconv/cache.py:34` — Python's `$` matches at end-of-string *or* immediately before a trailing `\n`, so `"USD\n"` satisfies the regex.
- Reproduction: `cache.CURRENCY_CODE_RE.match('USD\n')` returns a Match; `cache._cache_path('USD\n', 'EUR')` builds a path with no exception, and a real write attempt in an isolated temp dir raised `OSError [Errno 22] Invalid argument` rather than escaping the cache dir.
- **Blast radius assessment**: still fully anchored against `/`/`\`, so this does **not** enable path traversal. On Windows it reaches the same unhandled-OSError crash as finding 1; on POSIX a trailing `\n` is a legal filename byte and the write would likely succeed, producing an odd-but-contained artifact.
- **Exploitability x blast radius**: Medium x Low — a real validation-invariant violation, but degrades to finding 1's crash rather than to traversal.

**Explicitly ruled out (checked, not assumed)**:
- **Path traversal via `_cache_path`**: rejected correctly for every payload tried.
- **SSRF**: URL is built from a hardcoded `API_BASE_URL`; currency codes only ever land in the query string.
- **Unsafe deserialization**: both files use `json.loads`, which cannot execute code.
- **Injection**: no `subprocess`, `os.system`, `eval`, `exec`, or string-formatted SQL/shell anywhere.
- **Log/terminal injection**: currency codes are only ever printed via `!r` (`repr()`), which escapes control characters.

RISKS AND UNKNOWNS

- Did not verify whether `cache.set()`'s non-atomic write can produce a truncated cache file under concurrent invocations.

LESSON CANDIDATE
Mocking the dependency you're testing around can make a "no raw traceback" test pass while the real, unmocked code path crashes with exactly the traceback the test claims to rule out — a test asserting "no exception escapes main()" should exercise at least one real, unmocked validation path, not only the mocked-happy-path trigger for that exception.
