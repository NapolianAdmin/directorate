RISKS AND UNKNOWNS
- My tests patch `fxconv.cache.get/set/is_fresh` and `fxconv.rates.fetch_rate` as module attributes, which works because `cli.py` does `from fxconv import cache, rates` (module references, not `from fxconv.cache import get`) — this is confirmed correct by the passing tests and will keep working once the other two implementers fill in real logic, since real internal behavior is fully bypassed by the patches.
- `cli.py`'s exception handling only catches `rates.RatesError`; `convert()`'s docstring also mentions `ValueError` propagating from `fxconv.cache` on invalid currency codes — that is intentionally NOT caught by `main()` per the stub docstring (only `RatesError` is named as the thing `main()` must handle cleanly), so a malformed-but-not-API-rejected code shape could still raise a raw `ValueError` traceback through `main()`. This matches the documented contract exactly as written in the stub, but is worth the chief flagging if cache.py's real `_cache_path()` validation surfaces `ValueError` for cases the mission's "malformed currency code" test expects to be clean.

BLOCKERS
None.

LESSON CANDIDATE
When stub docstrings specify a module reference import style (`from fxconv import cache, rates` rather than `from fxconv.cache import get`), tests can safely `patch.object()` the submodule's function attributes directly and the patch will reach the code under test — worth calling out explicitly in future work orders so implementers don't default to `patch("fxconv.cli.cache.get")`-style targeting unnecessarily.
