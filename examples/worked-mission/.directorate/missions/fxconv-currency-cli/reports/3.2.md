WHAT I CHANGED
`fxconv/cache.py`:
1. `CURRENCY_CODE_RE = re.compile(r"^[A-Z]{3}$")` -> `re.compile(r"^[A-Z]{3}\Z")` — `\Z` matches only the true end of string, unlike `$` which matches before a trailing `\n`.
2. `set()` now writes the JSON payload to a unique temp file in the same directory and calls a retry-wrapped `os.replace` to atomically rename it into place, instead of `path.write_text(...)` directly on the final path. On any exception the temp file is cleaned up before re-raising. The retry wrapper (10 attempts, 10ms delay) absorbs a real, reproducible Windows quirk: `os.replace()` can transiently raise `PermissionError` when a reader concurrently has the destination open (Python's `open()` doesn't request `FILE_SHARE_DELETE` on Windows). This doesn't weaken atomicity — the rename still either fully succeeds or is retried; a reader never sees a partial file either way.
3. `is_fresh()` now computes `age = now - entry.fetched_at; return 0 <= age < ttl_seconds` instead of `(now - entry.fetched_at) < ttl_seconds`, so a negative age (future `fetched_at`, i.e. backward clock skew) is correctly treated as not fresh.

`tests/test_cache.py`: added 11 new tests (36 -> 47 total): trailing-newline rejection at three call sites, a new `TestAtomicWrite` class (monkeypatch proof `os.replace` is called with a sibling temp file already containing the full payload; proof `write_text` is never called on the final path directly; a deterministic real-thread concurrency test using a `threading.Event` handshake proving a concurrent reader on the final path only ever sees the complete old entry, never a partial new one), and `TestIsFresh` additions (backward clock skew by 10s and 1s -> not fresh; `now == fetched_at` boundary -> still fresh).

LESSON CANDIDATE
On Windows, `os.replace()` can raise a transient `PermissionError` when the destination file is concurrently open for reading elsewhere. A deterministic interleaving test (pause the write via monkeypatch + `threading.Event`, release a reader at the exact halfway point) is faster and more reliable than a raw race between tight-loop threads for proving an atomic-write property, and isolates the property under test from unrelated OS scheduling/locking quirks.
