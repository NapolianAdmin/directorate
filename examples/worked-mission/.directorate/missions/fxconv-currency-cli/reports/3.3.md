WHAT I CHANGED
- `fxconv/cli.py`:
  - Added `import math`.
  - In `main()`, added amount validation right after `parser.parse_args(argv)` and before `convert()` is called: rejects non-finite amounts (`not math.isfinite(args.amount)` — catches nan and +/-inf) and negative amounts (`args.amount < 0`), each printing a clean `f"{PROG}: error: ...}"` line to stderr and returning `1`. Zero is left untouched (still valid).
  - Widened the `except` clause around `convert()` from `except rates.RatesError as exc:` to `except (rates.RatesError, ValueError, OSError) as exc:`, so `ValueError` from `fxconv.cache._cache_path()` (bad currency-code format) and `OSError`/`PermissionError` from filesystem failures are now caught and reported the same clean way instead of propagating as raw tracebacks.
- `tests/test_cli.py`: added 5 new tests to `TestMain` — cache-layer `ValueError` clean exit, cache-layer `OSError`/`PermissionError` clean exit, nan amount rejected cleanly, negative amount rejected cleanly, zero amount still accepted.

LESSON CANDIDATE
When a CLI's documented error-handling contract names one exception type but a call chain crosses into another module with its own validation raising a different type, the docstring/spec for the caller should enumerate the full transitively-reachable exception surface, not just the immediate dependency's public exception type — otherwise the boundary between "documented, handled" and "leaks as a traceback" silently depends on which module happens to raise first.
